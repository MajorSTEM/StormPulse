# StormPulse V2 — Weighted T1/T2/T3 Confidence Scoring Methodology

**Module:** `backend/app/scoring/confidence.py`
**Validation:** `scripts/validate_scoring.py` against `scripts/fixtures/historical_events.json`
**Status:** Validated at **20/20 (100%) tier alignment** across 20 historical NWS events (acceptance: ≥ 85%).

StormPulse serves three kinds of objects — NWS alerts, Local Storm Reports (LSRs), and
damage corridors — and every one of them carries a confidence tier:

| Tier | Label | Meaning |
|------|-------|---------|
| **T1** | Official Confirmed | An official source has *confirmed* the claim (damage survey, confirmed tornado report) |
| **T2** | Official Near-Real-Time | An official source *asserts* the claim in near-real-time, without ground-truth confirmation (active warning, unverified report) |
| **T3** | Inferred (System Generated) | Only the StormPulse model asserts the claim. Always carries a disclaimer |

The model is **deterministic and reproducible**: it is a pure function with no clock
reads, no randomness, and no I/O. Same inputs ⇒ same tier ⇒ same score, every time.

---

## 1. The core principle: tier the *claim*, not the ingredients

Every object StormPulse serves is a **claim** ("a tornado occurred here", "damage runs
along this swath", "this area is under warning"). The tier answers one question:

> **Who is the most authoritative source asserting this claim?**

This is why an inferred corridor is T3 even when it was built from T1 tornado reports:
the *reports* are official claims about points, but the *swath* connecting them is
asserted only by our model. The reports keep their own T1/T2 tiers as separate map
objects; the corridor polygon carries T3 and a disclaimer.

## 2. Input signals and weights

Each claim is described by the set of evidence signals backing it. Every signal has a
named weight on a 0–1 scale encoding the authoritativeness of its source:

| Signal | Weight | What it is |
|--------|-------:|------------|
| `NWS_DAMAGE_SURVEY` | **1.00** | Official post-event NWS damage survey (DAT / Public Information Statement) |
| `CONFIRMED_TORNADO_LSR` | **0.90** | Tornado LSR (type T/TF/TW) from a trained spotter, emergency manager, or law enforcement |
| `OFFICIAL_WARNING_PRODUCT` | **0.60** | Active NWS Warning/Emergency product (radar-indicated or observed) |
| `OFFICIAL_WATCH_OR_ADVISORY` | **0.50** | Active NWS Watch, Advisory, or Statement |
| `UNCONFIRMED_LSR` | **0.45** | Near-real-time non-tornado storm report (wind, hail, …) — official channel, unverified content |
| `INFERRED_GEOMETRY` | **0.20** | Geometry/claim generated by the StormPulse Corridor Engine |

**Why these values:** the two confirmation-class signals sit at or above 0.90 because
each is, by itself, sufficient for "officially confirmed." The three near-real-time
official signals cluster in 0.45–0.60 — real, official, but unverified — ordered
Warning > Watch > unconfirmed report by product certainty. Inferred output sits far
below everything official at 0.20. The values were fixed by requiring that the model
reproduce analyst tier judgments on the 20-event historical fixture set (§5).

## 3. Tier assignment rule (dominant signal)

```
score = max( weight(s) for s in signals_present )

score ≥ 0.85          →  T1   (T1_THRESHOLD)
0.40 ≤ score < 0.85   →  T2   (T2_THRESHOLD)
score < 0.40          →  T3
empty signal set      →  T3, score 0.0
```

The tier score is the weight of the **dominant** (highest-weighted) signal — weights
are not summed. This is deliberate: provenance does not accumulate. A warning plus
fifty unconfirmed wind reports is still not a confirmation, so no pile of sub-T1
signals can ever cross the 0.85 line (the unit test
`test_weak_signals_never_accumulate_to_t1` locks this in). The thresholds partition
the weight scale so every signal maps to exactly one tier band
(`test_thresholds_partition_the_weight_scale`).

### How ingested objects map to signals

| Object | Signal set | Tier |
|--------|-----------|------|
| NWS alert, `*Warning` / `*Emergency` | `{OFFICIAL_WARNING_PRODUCT}` | T2 |
| NWS alert, Watch/Advisory/Statement | `{OFFICIAL_WATCH_OR_ADVISORY}` | T2 |
| LSR, type code T/TF/TW | `{CONFIRMED_TORNADO_LSR}` | T1 |
| LSR, any other type code | `{UNCONFIRMED_LSR}` | T2 |
| Engine-generated corridor | `{INFERRED_GEOMETRY}` | T3 |
| Flood-zone corridor (re-serves an official warning polygon verbatim) | `{OFFICIAL_WARNING_PRODUCT}` | T2 |

Adapters: `tier_for_alert()`, `tier_for_lsr()`, `tier_for_corridor()` in the scoring
module. These are the **only** places tier assignment happens — ingestion and the
corridor engine call them; no tier string is hardcoded anywhere else.

## 4. Worked examples (one per tier)

**T1 — Greenfield, IA tornado (2024-05-21).** An emergency manager confirms a tornado
on the ground while a Tornado Warning is active. Signals:
`{CONFIRMED_TORNADO_LSR (0.90), OFFICIAL_WARNING_PRODUCT (0.60)}`.
Dominant weight = 0.90 ≥ 0.85 ⇒ **T1**. The confirmed report alone carries the tier;
the warning adds nothing to provenance.

**T2 — Selma, AL tornado (2023-01-12), radar-indicated phase.** A Tornado Warning is
active on a radar debris signature, but no ground report has arrived yet. Signals:
`{OFFICIAL_WARNING_PRODUCT (0.60)}`. Dominant weight = 0.60 → 0.40 ≤ 0.60 < 0.85 ⇒
**T2**. Official and urgent, but not confirmation — the moment a spotter confirms it,
the confirmed LSR (0.90) arrives and the claim becomes T1.

**T3 — Bremen, KY corridor (2021-12-11), overnight reconstruction.** The Corridor
Engine chains tornado LSRs into a swath polygon hours before any survey exists. The
individual LSRs are T1 point objects, but the *swath* is asserted only by the model.
Signals for the corridor claim: `{INFERRED_GEOMETRY (0.20)}` → 0.20 < 0.40 ⇒ **T3**,
served with the disclaimer
`"INFERRED LAYER - System-generated estimate. Not an official NWS damage survey or warning product."`
in both the API payload and the map UI.

## 5. Validation against 20 historical NWS events

`scripts/validate_scoring.py` replays 20 historical events (2011 Joplin EF5 through
2024 Greenfield EF4 — see `scripts/fixtures/historical_events.json`) through
`assign_tier()`. Each fixture captures a claim at a stated observation snapshot, the
signals available at that snapshot, and the tier an analyst assigns under this rubric.
The set deliberately spans all three tiers (8 × T1, 7 × T2, 5 × T3) and includes
tier-boundary cases such as radar-indicated warnings without ground truth and
pre-survey overnight corridor reconstructions.

```
$ python scripts/validate_scoring.py
Tier alignment: 20/20 = 100.0% (acceptance: >= 85%)
Result: PASSED
```

The acceptance criterion from the implementation plan is **≥ 85%**; the shipped model
achieves **100%**. The script exits non-zero below the threshold, so it can gate CI.

## 6. Corridor confidence strength (HIGH / MEDIUM / LOW)

Orthogonal to the tier, each corridor also carries a **confidence score** answering a
different question: *given that this is an inferred claim, how strong is the evidence
behind it?* A T3 corridor can be HIGH confidence (dense, linear, warned track) and
still remains T3 — no official source asserts the swath.

Weighted additive model, capped at 1.0 (all constants named in the module):

| Component | Weight | Cap / condition |
|-----------|-------:|-----------------|
| Per confirmed tornado report in chain | +0.18 | capped at 0.45 |
| Per wind-damage report in chain | +0.04 | capped at 0.12 |
| Active NWS warning covers the chain | +0.15 | — |
| Track linearity (circular R of bearing pairs) | +0.18 / +0.10 / +0.04 | ≥ 0.85 / ≥ 0.65 / ≥ 0.40 |
| Inlier fraction (reports fitting the motion model) | +0.08 / +0.04 | ≥ 0.90 / ≥ 0.70 |

Labels: score ≥ 0.70 ⇒ **HIGH**, ≥ 0.40 ⇒ **MEDIUM**, else **LOW**.
Wind-swath and severe-weather corridors use the analogous count + warning models
(`compute_wind_confidence`, `compute_severe_confidence` — constants in the module).

**Worked example:** a chain with 3 tornado reports, 2 wind reports, an active warning,
track linearity 0.90, and all reports fitting the motion model scores
`0.45 (capped) + 0.08 + 0.15 + 0.18 + 0.08 = 0.94` ⇒ **HIGH** — and is still **T3**.

## 7. Reproducing and extending

- Unit tests: `cd backend && python -m pytest tests/test_confidence.py` (41 tests:
  determinism, threshold partitioning, caps, adapters, label boundaries).
- Validation: `python scripts/validate_scoring.py` from the repo root.
- Changing any weight or threshold requires re-running both; the validation harness
  fails the build below 85% alignment.
